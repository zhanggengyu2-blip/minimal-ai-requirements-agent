# V3.0 第三轮 QA 决策记录

> 确认日期：2026-08-22

## 1. 用户确认结果

| 编号 | 决定 |
|---|---|
| Q1 | 部署在一台长期在线的公司内网服务器或共享主机，通过统一 HTTPS 地址访问 |
| Q2 | 按内部正式工具运行：开机自启、异常重启、健康检查、轮转日志，不采购外部监控服务 |
| Q3 | 当前不建立备份策略，项目正式上线后再规划；接受策略落地前数据不可恢复风险 |
| Q4-1 | 首次注册使用部门＋姓名＋邀请码；后续登录使用部门＋姓名＋公司统一密码 |
| Q4-2 | 暂不处理离职用户停用；保留记录，也继续允许其登录 |
| Q5 | 会话空闲 7 天失效、最长 30 天，有效使用时滚动续期 |
| Q6 | 后端和非视觉基础先开发；团队任务与版本排期正式页面等待新版设计冻结 |
| Q7 | 任意项目成员均可归档或重新打开项目，不增加项目生命周期权限层级 |
| Q8 | 使用 GitHub Actions 作为合并前自动质量门禁 |

## 2. 第三轮形成的实现边界

- 系统是共享实例，不支持每名成员各运行一套独立数据；
- 前后端推荐同域部署，Cookie 只通过 HTTPS 传输；
- 公司统一密码是部署配置，不进入用户表；
- 同部门姓名唯一，不同部门允许同名；
- 邀请码只负责首次注册，管理员列表持续保存并允许复制；
- 不提供个人密码、密码找回、用户停用、用户删除或离职处理；
- 没有自动备份、回收站和操作审计，正式数据在策略补齐前可能永久丢失；
- 设计门禁只阻止正式业务页面，不阻止后端、迁移、路由、测试和构建基础建设。

## 3. 已接受风险

1. 知道公司统一密码且仍能访问内网的已注册用户可以继续登录，包括离职人员；
2. 统一密码泄露会影响全部用户，需要通过更换部署配置统一轮换；
3. 备份策略落地前，磁盘损坏、误删除或迁移失败可能导致全部数据不可恢复；
4. 任意项目成员都能归档项目，可能发生误操作；项目可由任意成员重新打开；
5. 设计未冻结前开始正式页面开发会增加返工，因此只允许先做非视觉基础。

## 4. GitHub Actions 的作用

每次推送或合并请求由 GitHub 在干净环境自动执行：

- 后端依赖安装和 pytest；
- 前端锁文件安装、类型检查、单元测试和生产构建；
- OpenAPI 重新生成，并检查前端 TypeScript 类型没有漂移；
- 关键阶段再增加 Playwright 浏览器闭环。

GitHub Actions 只做代码质量检查。本期不会用它自动部署、执行数据库迁移、清空数据或修改共享服务器。
