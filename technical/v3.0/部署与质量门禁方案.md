# V3.0 部署与质量门禁方案

> 状态：第三轮 QA 已确认
> 目标：共享内网单实例、可持续运行、合并前自动验证

## 1. 部署拓扑

```text
团队浏览器
    ↓ HTTPS
内网反向代理（统一域名）
    ├── 前端静态文件
    └── /api/v1 → FastAPI 单实例
                         ├── SQLite 本地磁盘
                         ├── 访谈附件目录
                         └── Dify Workflow
```

约束：

- 部署在长期在线的公司内网服务器或共享主机；
- 前后端使用同一 HTTPS 域名；
- FastAPI 只运行一个实例，SQLite 文件位于本地磁盘；
- 不把数据库放在网络共享目录；
- 每名成员通过浏览器访问同一套数据，不各自运行本地实例。

TLS、HSTS、CSP、`X-Content-Type-Options` 等统一安全响应头由内网反向代理配置；FastAPI 保留 HttpOnly/SameSite/Secure Cookie、CSRF 和本地开发 CORS 责任。

## 2. 运行保障

- 操作系统启动后自动启动反向代理和后端；
- 后端异常退出后自动重启，并限制连续失败重启频率；
- `/health` 检查进程存活，`/ready` 检查数据库连接和迁移版本；
- 日志按大小或日期轮转，设置容量上限；
- 日志不得记录邀请码、统一密码、会话令牌或附件内容；
- 本期不接入付费监控、短信、邮件或即时通讯告警。

## 3. 配置和密钥

生产环境至少独立配置：

- 数据库绝对路径；
- 公司统一登录密码；
- 会话令牌密钥；
- CSRF 密钥；
- 邀请码摘要密钥；
- 邀请码加密密钥；
- Cookie 名称、域名、Secure 与 SameSite；
- Dify 地址和两个 Workflow API Key；
- 允许的外部来源和附件目录。

生产密钥只存在于共享服务器的受限环境文件或密钥存储，不提交 Git，不写入构建产物。

## 4. 当前备份边界

第三轮决定当前不建立备份策略，正式上线后再规划。因此本期没有自动备份任务，也不把备份恢复演练设为首次上线门禁。

已知后果：在后续策略落地前，SQLite 数据库和访谈附件都没有灾难恢复保证。永久删除任务、磁盘故障或主机损坏可能造成不可恢复的数据丢失。

## 6. GitHub Actions 门禁

已建立 `.github/workflows/quality.yml`，包含以下工作流：

1. 后端：安装固定依赖，执行全部 pytest；
2. 前端：使用固定 Node 和 pnpm 版本执行锁文件安装；
3. 前端：执行 TypeScript/Vue 类型检查、Vitest 和生产构建；
4. 契约：重新生成 OpenAPI 和前端类型，检查 Git 工作区无差异；
5. 端到端：使用一次性 SQLite 库运行 1280×900 Playwright 关键闭环。

门禁会在合并请求执行，并在 `main` / `master` 分支推送后再次验证；它不自动部署共享服务器，不执行 Alembic，不接触正式数据库。
