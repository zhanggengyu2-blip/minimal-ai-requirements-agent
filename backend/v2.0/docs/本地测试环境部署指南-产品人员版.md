# 极简 AI 团队需求管理智能体：本地测试环境部署指南

适用对象：产品经理、测试人员、第一次接触 Python 后端的非开发人员。
适用系统：优先面向当前项目所在的 macOS；文末补充 Windows PowerShell 命令。
后端技术：FastAPI + SQLite + 本地 Docker Dify Workflow。

---

## 一、部署完成后会得到什么

完成本指南后，本机将运行一个后端服务：

```text
http://127.0.0.1:8000
```

常用地址：

| 地址                                    | 作用                             |
| --------------------------------------- | -------------------------------- |
| `http://127.0.0.1:8000/api/v1/health` | 检查后端是否启动                 |
| `http://127.0.0.1:8000/docs`          | FastAPI 自带的 Swagger 接口页面  |
| `http://127.0.0.1:8000/openapi.json`  | Apifox 可导入的 OpenAPI 接口定义 |

业务数据默认保存在：

```text
backend/v2.0/data/requirements.db
```

Dify 仍由本地 Docker 独立运行。FastAPI 只调用 Dify，不会把业务数据库交给 Dify。

## 二、环境依赖清单

### 1. Python

推荐版本：

```text
Python 3.12.x 正式版
```

最低代码要求为 Python 3.11，但不建议使用带有以下标记的测试版本：

```text
3.11.0a...
3.11.0b...
3.11.0rc...
```

其中 `a/b/rc` 分别表示 Alpha、Beta、Release Candidate，并非正式稳定版。当前项目已使用 Python 3.12.13 完成自动化测试。

检查版本：

```bash
python3.12 --version
```

预期类似：

```text
Python 3.12.13
```

如果命令不存在，需要先安装 Python 3.12 正式版，然后重新打开终端。

### 2. Dify

需要：

- 本地 Docker 中的 Dify 已启动；
- 需求分析 Workflow 已发布；
- 已取得该 Workflow 的 API Key；
- 知道 Dify 对宿主机暴露的 API 地址。

常见基础地址：

```text
http://127.0.0.1/v1
```

如果本地 Dify 使用其他端口，例如 8080，则可能是：

```text
http://127.0.0.1:8080/v1
```

这里需要的是 Dify Workflow 应用 API Key，通常以 `app-` 开头，不是模型厂商密钥，也不是 Dify 登录密码。

### 3. SQLite

不需要单独安装数据库服务。

项目通过 Python 自带的 SQLite 能力使用一个本地 `.db` 文件。首次启动时会自动创建目录、数据库文件和数据表。

### 4. Apifox

Apifox 不是启动后端所必需的工具，仅用于图形化接口调试。

### 5. `requirements.txt` 依赖说明

后端目录 `backend/v2.0` 已经提供：

```text
requirements.txt
```

其中版本均为当前已验证版本。

| 依赖                  | 作用                                     |
| --------------------- | ---------------------------------------- |
| `fastapi`           | 提供后端 API、参数校验和 Swagger 文档    |
| `uvicorn[standard]` | 启动 FastAPI Web 服务                    |
| `httpx`             | 异步调用 Dify Workflow HTTP API          |
| `pydantic-settings` | 读取`.env` 配置并校验参数              |
| `SQLAlchemy`        | 将 Python 对象映射到 SQLite 表并执行查询 |
| `pytest`            | 运行自动化测试                           |
| `pytest-asyncio`    | 支持测试异步代码                         |

`requirements.txt` 是为了让非开发人员一条命令安装完整测试环境。`pyproject.toml` 则是开发和打包使用的项目正式依赖声明。

## 三、macOS 分步启动

下面的命令可以逐段复制到 macOS“终端”执行。

### 第 1 步：进入项目目录

```bash
cd '<仓库目录>/backend/v2.0'
```

确认当前位置：

```bash
pwd
```

预期输出：

```text
<仓库目录>/backend/v2.0
```

### 第 2 步：确认 Python 版本

```bash
python3.12 --version
```

应为 Python 3.12.x 正式版。

### 第 3 步：创建虚拟环境

仅在第一次部署时执行：

```bash
python3.12 -m venv .venv
```

虚拟环境可以理解为项目自己的 Python 工具箱，避免和电脑中其他 Python 项目互相影响。

如果 `.venv` 已存在，不需要重复创建。

### 第 4 步：激活虚拟环境

每次新打开终端都需要执行：

```bash
source .venv/bin/activate
```

成功后，终端命令行前面通常会显示：

```text
(.venv)
```

确认当前 Python 来自项目虚拟环境：

```bash
which python
```

路径应包含：

```text
极简AI团队需求管理智能体/backend/v2.0/.venv/bin/python
```

### 第 5 步：安装依赖

第一次部署或 `requirements.txt` 更新后执行：

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

最后出现类似以下内容表示安装成功：

```text
Successfully installed ...
```

### 第 6 步：创建本地配置文件

仅在第一次部署时执行：

```bash
cp -n .env.example .env
```

`-n` 表示如果 `.env` 已经存在就不覆盖，避免丢失已填写的密钥。

使用系统文本编辑器打开：

```bash
open -e .env
```

至少需要确认以下配置：

```dotenv
APP_NAME=极简AI团队需求管理智能体
APP_ENV=development
DEBUG=true
API_V1_PREFIX=/api/v1
DATABASE_URL=sqlite:///./data/requirements.db

DIFY_BASE_URL=http://127.0.0.1/v1
DIFY_API_KEY=app-替换为真实Workflow密钥
DIFY_WORKFLOW_PATH=/workflows/run
DIFY_TIMEOUT_SECONDS=8
DIFY_CANDIDATE_LIMIT=30
```

保存并关闭文本编辑器。

### 第 7 步：确认 Dify 正在运行

先在浏览器中打开本地 Dify 管理页面，确认：

- 页面可以访问；
- Workflow 已发布；
- Workflow 可以在 Dify 页面中成功运行。

如果不知道 Dify 暴露端口，可查看 Docker Desktop 中 Dify 相关容器的 Port 映射。

### 第 8 步：启动后端

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

看到类似以下输出表示启动成功：

```text
Uvicorn running on http://127.0.0.1:8000
Application startup complete.
```

注意：

- 启动后不要关闭这个终端窗口；
- `--reload` 适合本地测试，代码变化时会自动重启；
- 按 `Control + C` 可以停止服务。

### 第 9 步：检查健康状态

新开一个终端窗口，执行：

```bash
curl http://127.0.0.1:8000/api/v1/health
```

预期响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "status": "ok"
  },
  "request_id": "一串请求ID"
}
```

也可以直接在浏览器打开：

```text
http://127.0.0.1:8000/docs
```

### 第 10 步：运行项目自测

先停止 Uvicorn，或在另一个已激活虚拟环境的终端中执行：

```bash
python -m pytest -q
```

预期：

```text
5 passed
```

这些测试会模拟 Dify，不会调用真实模型，也不会写入正式的 `data/requirements.db`。

## 四、以后每天如何启动

完成首次安装后，以后通常只需要：

```bash
cd '<仓库目录>/backend/v2.0'
source .venv/bin/activate
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

同时确认 Docker Desktop 中的 Dify 已启动。

停止后端：

```text
在运行 Uvicorn 的终端按 Control + C
```

退出虚拟环境：

```bash
deactivate
```


```powershell

```

## 六、全局配置说明

配置文件位置：

```text
backend/v2.0/.env
```

修改 `.env` 后必须停止并重新启动后端，配置才会重新加载。

### 1. 应用配置

| 配置              | 默认值                   | 说明                         |
| ----------------- | ------------------------ | ---------------------------- |
| `APP_NAME`      | 极简AI团队需求管理智能体 | Swagger 中显示的项目名称     |
| `APP_ENV`       | `development`          | 环境标识，目前不影响业务逻辑 |
| `DEBUG`         | `true`                 | 本地是否开启调试模式         |
| `API_V1_PREFIX` | `/api/v1`              | 接口统一前缀，不建议随意修改 |

### 2. Dify 配置

| 配置                     | 示例                    | 说明                             |
| ------------------------ | ----------------------- | -------------------------------- |
| `DIFY_BASE_URL`        | `http://127.0.0.1/v1` | Dify API 基础地址                |
| `DIFY_API_KEY`         | `app-xxxxxxxx`        | 已发布 Workflow 的 API Key       |
| `DIFY_WORKFLOW_PATH`   | `/workflows/run`      | Dify Workflow 调用路径           |
| `DIFY_TIMEOUT_SECONDS` | `8`                   | 单条分析最长等待秒数             |
| `DIFY_CANDIDATE_LIMIT` | `30`                  | 传给 Dify 用于查重的历史候选上限 |

完整调用地址由后端自动拼接：

```text
DIFY_BASE_URL + DIFY_WORKFLOW_PATH
```

例如：

```text
http://127.0.0.1/v1/workflows/run
```

#### 如何获取正确的 Dify API Key

1. 打开 Dify；
2. 进入当前需求分析 Workflow 应用；
3. 打开 API 访问或 API Access 页面；
4. 创建或复制应用 API Key；
5. 填入 `.env` 的 `DIFY_API_KEY`；
6. 重启 FastAPI。

不要填写：

- OpenAI/DeepSeek/通义千问模型密钥；
- Dify 登录密码；
- 知识库 API Key；
- 其他 Dify 应用的 API Key。

### 3. SQLite 配置

默认：

```dotenv
DATABASE_URL=sqlite:///./data/requirements.db
```

含义：

- `sqlite:///`：使用 SQLite；
- `./data/`：固定相对于后端目录 `backend/v2.0`；
- `requirements.db`：数据库文件名。

程序会把相对数据库路径解析到 `backend/v2.0`，不会因为终端当前目录不同而生成另一份数据库。日常操作仍建议先进入该目录，便于执行依赖安装和测试命令。

首次启动后：

```text
data/
└── requirements.db
```

备份数据库最简单的方式：

1. 先按 `Control + C` 停止后端；
2. 复制 `data/requirements.db` 到安全目录；
3. 不要在后端运行中用文本编辑器打开或修改数据库文件。

如果要把数据库放到绝对路径，可填写：

```dotenv
DATABASE_URL=sqlite:////Users/你的用户名/Documents/minimal-ai-data/requirements.db
```

macOS 绝对路径在 `sqlite:` 后需要四个 `/`。

### 4. 后端端口配置

当前端口不是从 `.env` 读取，而是在启动命令中设置：

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

如果 8000 被占用，改成 8001：

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 --reload
```

对应地址也变成：

```text
http://127.0.0.1:8001
```

此时需要同步修改：

- Apifox 本地环境前置 URL；
- 前端请求后端的基础地址；
- 手工执行的 curl 地址。

### 5. 前端端口与 CORS

当前后端只明确允许以下本地前端来源：

```text
http://localhost:3000
http://127.0.0.1:3000
```

配置位置：

```text
app/main.py
```

如果前端运行在 5173 端口，浏览器可能提示 CORS 错误，需要开发人员把：

```text
http://localhost:5173
http://127.0.0.1:5173
```

加入 `allow_origins`，然后重启后端。

Apifox 和 curl 通常不受浏览器 CORS 限制。

## 七、常见启动报错排查清单

### 1. `command not found: python3.12`

现象：

```text
zsh: command not found: python3.12
```

原因：没有安装 Python 3.12，或安装后终端尚未刷新。

处理：

1. 安装 Python 3.12 正式版；
2. 关闭并重新打开终端；
3. 执行 `python3.12 --version`；
4. 不要使用显示 `b`、`a` 或 `rc` 的测试版本。

### 2. `No module named fastapi` / `No module named sqlalchemy`

原因：

- 没有激活虚拟环境；
- 依赖没有安装；
- 使用了电脑中另一个 Python。

依次执行：

```bash
cd '<仓库目录>/backend/v2.0'
source .venv/bin/activate
which python
python -m pip install -r requirements.txt
```

然后再启动。

### 3. `Address already in use`

现象：

```text
[Errno 48] Address already in use
```

原因：8000 端口已被另一个程序占用，最常见的是上一次后端仍在运行。

查看占用者：

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

优先处理：

1. 找到之前运行 Uvicorn 的终端，按 `Control + C`；
2. 如果无法找到，直接改用 8001 端口。

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 --reload
```

不要随意结束不认识的系统进程。

### 4. 浏览器显示“无法访问此网站”

检查：

1. 启动 Uvicorn 的终端是否仍然打开；
2. 是否出现 `Application startup complete`；
3. 浏览器地址是否使用正确端口；
4. 是否误用了 `https://`。本地默认是 `http://`；
5. 先访问 `/api/v1/health`。

### 5. Dify API Key 未配置

需求创建响应可能包含：

```json
{
  "code": "AI_ANALYSIS_FAILED",
  "data": {
    "analysis_status": "FAILED",
    "analysis_error_code": "DIFY_NOT_CONFIGURED"
  }
}
```

处理：

1. 打开 `.env`；
2. 确认不是示例值 `app-your-workflow-api-key`；
3. 确认没有多余引号和空格；
4. 保存；
5. 完整重启 FastAPI。

### 6. Dify 密钥错误或过期

表现：

```text
analysis_error_code = DIFY_HTTP_ERROR
```

可能同时记录 HTTP 401。

处理：

1. 确认 Key 来自当前 Workflow 应用；
2. 在 Dify 中重新生成应用 API Key；
3. 替换 `.env`；
4. 重启 FastAPI；
5. 再提交一条新需求测试。

注意：创建需求本身仍可能返回 HTTP 201，因为原始需求已经成功保存；要查看响应中的业务 `code` 和 `analysis_status`。

### 7. 无法连接 Dify

表现：

```text
analysis_error_code = DIFY_CONNECTION_ERROR
```

排查：

1. Docker Desktop 是否启动；
2. Dify 容器是否全部正常；
3. `DIFY_BASE_URL` 端口是否正确；
4. 浏览器能否访问 Dify；
5. FastAPI 运行在宿主机时，优先使用 Dify 对宿主机暴露的地址；
6. 修改配置后是否重启 FastAPI。

### 8. Dify 调用超时

表现：

```text
analysis_error_code = DIFY_TIMEOUT
```

处理顺序：

1. 在 Dify 页面直接运行同一 Workflow，观察耗时；
2. 检查模型、知识检索或代码节点是否卡住；
3. 检查 Docker 资源是否不足；
4. 本地调试时可暂时把 `DIFY_TIMEOUT_SECONDS=8` 调为 `15`；
5. 重启 FastAPI。

不要一开始就把超时设置成几分钟。当前单条分析目标应控制在十几秒内。

### 9. AI 返回格式错误

表现：

```text
analysis_error_code = DIFY_OUTPUT_INVALID
```

原因通常是：

- Dify 结束节点没有输出完整 10 字段；
- Boolean 被输出为字符串；
- `type` 或 `priority` 不属于固定枚举；
- `is_duplicate` 与 `related_id` 矛盾；
- 模型返回的 `related_id` 不在候选列表中。

处理：

1. 打开 Dify 本次运行日志；
2. 查看结束节点 `outputs`；
3. 对照 `../../../product/v1.1/ai/dify-rag/04-Dify固定输出-JSON-Schema.json`；
4. 不要通过放宽后端校验来掩盖 Workflow 输出错误。

### 10. 数据库无法创建或写入

可能出现：

```text
unable to open database file
attempt to write a readonly database
Permission denied
```

处理：

1. 确认 `backend/v2.0/data` 是普通目录而不是符号链接；
2. 确认后端目录有写权限；
3. 执行：

```bash
mkdir -p data
chmod u+rwX data
```

4. 检查 macOS 是否限制终端访问“文稿/Documents”目录；
5. 不要把 `DATABASE_URL` 指向只读目录；
6. 停止可能正在锁定该文件的数据库工具。

### 11. `database is locked`

原因：

- 同时运行多个后端进程；
- 数据库查看工具正在编辑 SQLite；
- 上一个写事务未释放。

处理：

1. 停止所有 Uvicorn 窗口；
2. 关闭正在编辑数据库的工具；
3. 确认 8000 端口没有残留后端；
4. 再启动一个 Uvicorn 实例。

不要在不清楚用途时删除 `.db-wal` 或 `.db-shm` 文件。

### 12. 项目名称已存在

响应：

```text
HTTP 409
code = CONFLICT
message = 项目名称已存在
```

处理：在测试 JSON 中换一个项目名称，或直接使用已有项目 ID。

### 13. 请求参数校验失败

响应：

```text
HTTP 422
code = VALIDATION_ERROR
```

常见原因：

- `project_id` 不是 32 位；
- `raw_content` 为空或全是空格；
- `page=0`；
- `page_size` 超过 100；
- `priority=P9`；
- 批量请求超过 50 条或存在重复 ID。

根据响应中的 `details` 查找具体字段。

### 14. 修改 `.env` 后没有生效

原因：配置在应用启动时读取并缓存。

处理：

1. 在 Uvicorn 终端按 `Control + C`；
2. 确认 `.env` 已保存；
3. 重新执行启动命令。

不要依赖 `--reload` 自动识别所有 `.env` 变化。

### 15. 前端出现 CORS 错误

表现：Swagger、curl、Apifox 正常，但浏览器前端失败。

原因：前端地址不在 `app/main.py` 的 `allow_origins` 中。

处理：让开发人员添加实际前端地址，然后重启后端。

## 八、建议的验收顺序

不要一开始就测试所有接口，按以下顺序定位问题最快：

1. Docker 中确认 Dify Workflow 能单独运行；
2. 启动 FastAPI；
3. 调用健康检查；
4. 创建一个唯一名称的项目；
5. 查询项目列表并取得项目 ID；
6. 创建需求；
7. 检查 `analysis_status` 是否为 `ANALYZED`；
8. 查询需求列表；
9. 查询需求详情；
10. 再做无效参数、错误项目 ID、错误密钥等异常测试。
