# 极简 AI 团队需求管理智能体：后端文件分层与字段说明

> 更新日期：2026-09-29。核对基线：当前 `main` 的 `8403a1c`。
> 本文按实际源码整理，用于后端代码 review。后端源码使用稳定的 `backend/` 目录，产品版本基线独立归档。

本文帮助你回答：文件属于哪一层、关键字段表示什么、一次请求经过哪些文件、改动某个业务规则时应该从哪里看起。相对路径和命令均以 `backend` 为起点。

当前包含 **14 张业务表、14 组 ORM 枚举、6 个 Alembic 迁移、51 个业务接口操作**。迁移版本表 `alembic_version` 不计入业务表；`/docs`、`/openapi.json` 等框架接口不计入上述接口数。

## 一、先理解分层

| 层次 | 文件位置 | 负责什么 | Review 时重点看什么 |
| --- | --- | --- | --- |
| 应用入口 | `app/main.py` | 创建 FastAPI、注册 CORS、请求 ID、异常处理和总路由 | 应用如何组装；错误如何返回 |
| 全局基础能力 | `app/core/` | 配置、稳定路径、安全工具和业务异常 | 配置来源、摘要与加密、错误码 |
| 请求依赖 | `app/api/deps.py` | 数据库会话、登录身份、CSRF、管理员检查 | 谁能进入接口、写请求怎样校验 |
| API 路由 | `app/api/router.py`、`app/api/routes/` | 接收 HTTP 参数、调用业务、返回响应 | 路径、请求 Schema、身份传递、访问检查 |
| 数据合同 | `app/schemas/` | Pydantic 请求校验、响应字段和 Dify 输出校验 | 必填、可空、默认值、长度和跨字段规则 |
| 业务逻辑 | `app/services/` | 项目权限、状态流转、排序、并发检查、事务及外部调用 | 业务约束在哪里执行，失败后留下什么 |
| 数据库模型 | `app/db/models.py` | SQLAlchemy 表、字段、关系、索引及约束 | 哪些关系由数据库保证，哪些由 Service 保证 |
| 连接与初始化工具 | `app/db/session.py`、`migrations.py`、`seed.py` | 数据库连接、迁移调用、默认部门初始化 | 建表、种子数据、运行期 Session 是否分开 |
| 结构版本管理 | `migrations/`、`alembic.ini` | 从历史结构升级到当前结构 | 迁移顺序、已有数据前提、升级与回退 |
| 辅助工具与测试 | `scripts/`、`tests/` | 管理员初始化、合同导出、自动化验证 | 是否覆盖约束、权限、并发和错误分支 |

一次普通业务请求大致是：

```text
HTTP 请求
  → main.py：请求 ID、中间件和异常处理
  → api/router.py + api/deps.py：路由挂载、会话身份和 CSRF
  → api/routes/*.py + schemas/*.py：参数校验与请求分发
  → services/*.py：业务检查、查询/写入、必要时调用 Dify
  → db/models.py + db/session.py：数据库操作
  → Read Schema → ApiResponse → 前端
```

这是职责导航，不表示 FastAPI 所有依赖和参数校验都严格按图中顺序执行。当前代码中，需求与访谈的一部分项目访问检查在路由层完成，任务与版本的检查则主要放在 Service；review 时要连着看，不能仅凭 Service 方法名推断它已经做过鉴权。

## 三、数据库层：先认清业务对象与字段

### 3.1 Model 和 Schema 的区别

`db/models.py` 中的 `Task` 是数据库记录；`schemas/task.py` 中的 `TaskCreate` 是创建输入，`TaskRead` 是返回给前端的结构。字段同名不等于职责相同：

- `created_by`、`updated_by` 由后端根据登录身份填写，不由创建任务的请求指定。
- `expected_revision` 是客户端提交的并发校验值，不是单独保存的数据库列。
- `member_count`、`task_count` 等来自查询统计，不是对应主表里的计数列。
- `preview_url` 是附件模型的计算属性，不是磁盘路径或数据库列。
- `str | None` 只说明允许空值；Schema 未声明默认值时，字段仍可能是必填项。

### 3.2 通用约定

单列 `id` 通常由 `new_id()` 生成 32 位 UUID hex；`ProjectMember`、`VersionParticipant`、`TaskLane` 使用复合主键，并没有独立 `id`。时间由 `utc_now()` 按 UTC 写入；任务和版本日期使用 `Date`，不是时间戳。

ORM 枚举以字符串保存。ORM 的 `default=` / `onupdate=` 和迁移里的 `server_default=` 不是同一机制；检查直接 SQL 写入行为时，应同时查看迁移文件。

### 3.3 身份与组织：4 张表

| Model / 表 | 关键字段 | 含义与约束 |
| --- | --- | --- |
| `Department` / `department` | `id`、`name`、创建/更新时间 | 名称唯一；当前已没有 `status` 列，不再使用部门启用/停用模型 |
| `UserAccount` / `user_account` | `department_id`、`name`、`normalized_name`、`role`、`invitation_id` | 系统已注册用户；部门与规范化姓名联合唯一，允许不同部门同名；角色为 ADMIN/MEMBER；邀请码关联可空且唯一 |
| `AuthSession` / `auth_session` | `user_id`、`token_digest`、`idle_expires_time`、`absolute_expires_time`、`last_seen_time`、`revoked_time` | 每次登录的服务端会话；保存令牌摘要，不保存 Cookie 原文；空闲期限、绝对期限与撤销状态共同决定有效性 |
| `InvitationCode` / `invitation_code` | `code_digest`、`code_ciphertext`、`department_id`、`intended_user_name`、`status`、`used_by_user_id`、`created_by`、使用/停用时间 | 摘要用于匹配，密文用于管理员列表解密展示；可限定使用人姓名；注册成功后记录实际用户并核销 |

用户表没有个人密码列；统一密码来自配置。邀请码当前为 **9 位大写字母或数字**，不是旧文档里的 `XXXX-XXXX`。

部门引用使用 `RESTRICT`；业务上有用户、项目或邀请码引用时不能删除部门。用户关联会话使用 `CASCADE`；这些数据库删除策略不表示系统已经提供用户删除接口。

### 3.4 项目、任务与版本：6 张表

| Model / 表 | 关键字段 | 含义与约束 |
| --- | --- | --- |
| `Project` / `project` | `name`、`description`、`project_context`、`department_id`、`created_by`、`status`、`revision`、`member_revision` | 名称全局唯一；上下文供需求分析使用；资料版本号与成员集合版本号独立 |
| `ProjectMember` / `project_member` | `project_id + user_id`、`added_by`、`sort_order`、`created_time` | 复合主键；确定用户是否属于项目，以及项目内统一成员顺序 |
| `TaskLane` / `task_lane` | `project_id + assignee_id`、`revision`、`updated_time` | 复合主键；“某项目某负责人的任务集合/顺序”的并发标记，零任务成员也可以有泳道 |
| `Task` / `task` | `project_id`、`assignee_id`、`version_id`、`name`、`description`、`status`、`priority`、`start_date`、`due_date`、`sort_order`、`revision`、创建/更新人及时间 | 团队任务与版本排期共用的任务记录；负责人必须属于当前项目；版本和日期可空 |
| `ProjectVersion` / `project_version` | `project_id`、`name`、`start_date`、`end_date`、`status`、`revision`、创建/更新人及时间 | 同项目版本名唯一；起止日期必填，结束日期不得早于开始日期 |
| `VersionParticipant` / `version_participant` | `version_id + user_id`、`created_time` | 复合主键；记录版本参与人，没有独立排序列，展示顺序取自项目成员 |

这里有三个必须分清的关系：

1. 系统成员是 `UserAccount`；项目成员是 `ProjectMember`；版本参与人是 `VersionParticipant`。版本参与人必须先是项目成员，这条规则由 Service 校验。
2. 面板和版本排期查询同一张 `Task` 表。任务通过可空 `version_id` 归属一个版本；没有单独的“排期任务表”，也没有独立甘特图表。
3. `Task(project_id, assignee_id)` 有指向项目成员的复合外键；**`Task.version_id` 当前没有数据库外键**。同项目版本校验、补齐参与人、删除版本后清空关联均由业务层负责。

任务两个日期都有值时，数据库和业务层都要求 `due_date >= start_date`。当前代码不要求任务日期落在版本日期范围内。项目归档通过状态切换完成，并不触发数据库级联删除；当前也没有删除项目 API。

### 3.5 需求与访谈：4 张表

| Model / 表 | 字段分组 | 说明 |
| --- | --- | --- |
| `Requirement` / `requirement` | `project_id`、`raw_content`、`created_by` | 正式需求所属项目、原始输入和创建人 |
| 同上 | `interview_session_id`、`clarified_content`、`interview_rounds`、`completeness_score` | 访谈来源、整理正文、轮数和完整度；直接提交时可无访谈来源 |
| 同上 | `standard_content`、`business_goal`、`type`、`priority`、`is_fake`、`fake_reason`、`is_duplicate`、`related_id`、`reference_rule`、`analysis_summary` | 固定 10 个 AI 分析字段；未分析时部分字段可空，`related_id` 默认空字符串 |
| 同上 | `analysis_status`、`analysis_error_code`、`analysis_error_message`、`dify_workflow_run_id`、`manual_modify` | 分析进度、失败原因、运行追踪和人工修改标记；存在标记不代表已有对应编辑 API |
| `InterviewSession` / `interview_session` | `project_id`、`created_by`、`source_channel`、`source_user_id`、`source_message_id`、`entry_key`、`project_resolve_mode` | 来源与归属；当前创建接口由服务端固定管理端渠道和用户选择项目模式，渠道枚举不等于全部渠道已接入 |
| 同上 | `status`、`raw_content`、`request_type`、`structured_data`、`skipped_fields` | 状态和抽取内容；后两项以 JSON 字符串存入 TEXT，响应时转换为对象/列表 |
| 同上 | `completeness_score`、`round_count`、`consecutive_skip_count`、`consecutive_agent_failures`、`stop_reason` | 后端决定是否继续追问的依据 |
| 同上 | `summary_title`、`clarified_content`、`requirement_id`、`confirm_idempotency_key`、`agent_error_code`、`agent_error_message`、`prompt_version` | 总结、确认结果、幂等记录与 AI 错误追踪 |
| `InterviewMessage` / `interview_message` | `session_id`、`sequence_no`、`role`、`content`、`action_type`、`target_field`、`reason_code`、`client_message_id`、`agent_run_id` | 会话内顺序、消息角色、动作和客户端重试标识；会话+序号、会话+客户端消息 ID 各有唯一约束 |
| `InterviewAttachment` / `interview_attachment` | `session_id`、`message_id`、`uploaded_by`、`original_name`、`stored_name`、`storage_path`、`mime_type`、`size_bytes`、`sha256` | 先上传再绑定；磁盘存储字段不直接返回给前端 |
| 同上 | `dify_upload_file_id`、`dify_user` | 复用当前访谈身份已上传到 Dify 的图片，避免重复上传 |

`InterviewSession.requirement_id`、`Requirement.interview_session_id` 和 `Requirement.related_id` 是逻辑引用，不是数据库外键。会话到消息/附件是级联删除关系；消息删除时附件的 `message_id` 置空。附件记录的数据库删除也不等于磁盘文件已经自动删除。

## 四、数据库连接、迁移与初始化

### `app/db/base.py` 与 `app/db/session.py`

`base.py` 只定义 `DeclarativeBase`。`session.py` 创建 `engine`、`SessionLocal` 和依赖函数 `get_db()`：

- SQLite 相对文件路径在配置层解析，连接前创建父目录。
- `check_same_thread=False`，`pool_pre_ping=True`。
- SQLite 每次连接启用外键、`busy_timeout=5000`、WAL 和 `synchronous=NORMAL`。
- Session 设置 `autoflush=False`、`expire_on_commit=False`。
- `get_db()` 负责创建并最终关闭 Session；业务提交点由 Service 控制，不是在每次请求结束时自动 commit。

旧的 `init_db()` 和 `_migrate_v2_sqlite_requirement_columns()` 已不存在。启动 FastAPI 不会执行 `create_all()` 或自动补列。

### `app/db/migrations.py`、`migrations/env.py` 和迁移文件

`build_alembic_config()` 统一构建配置；`upgrade_database()` 升级指定数据库至 head；`current_revision()` 查询实际版本。迁移环境导入 `models` 填充 `Base.metadata`，SQLite 使用 batch 模式处理结构变更。

| 文件 | 主要变化 |
| --- | --- |
| `migrations/versions/0001_v3_baseline.py` | 建立原有部门、邀请码、项目、需求、访谈会话/消息/附件共 7 张表的基线 |
| `migrations/versions/0002_identity_auth.py` | 新增用户与登录会话；邀请码改为摘要和密文；删除部门状态列 |
| `migrations/versions/0003_project_members.py` | 项目成员、项目两类修订号、部门/创建人外键及历史项目成员回填 |
| `migrations/versions/0004_tasks_and_lanes.py` | 新增任务、泳道、日期约束、负责人复合外键和查询索引 |
| `migrations/versions/0005_project_member_order.py` | 增加并回填项目成员顺序，创建排序索引 |
| `migrations/versions/0006_project_versions.py` | 新增项目版本和参与人，当前 head |

Review 历史库升级时注意源码中的实际前提：0002 要求旧邀请码表为空；0003 遇到已有项目时要求先有管理员，用于补齐历史创建人和成员。因此不能把“空库可一次升级到 head”理解成“任何历史数据都可直接无损升级”。

### `app/db/seed.py` 与 `scripts/bootstrap_admin.py`

`seed_default_departments()` 只补齐缺少的“运营部、产品部、销售部”，不会清空或重建表。`bootstrap_admin.py` 调用 `AuthService.bootstrap_admin()` 创建首个管理员；已有 ADMIN 时会拒绝再次执行。

全新本地库的初始化顺序：

```bash
python -m alembic upgrade head
python -m app.db.seed
python scripts/bootstrap_admin.py --department 产品部 --name 本地验收管理员
```

最后一条仅用于尚无管理员的系统。已有环境只按实际需要升级迁移，不要重复当成新库初始化。

## 五、Schema 层：按模块定位输入与输出

所有路径均位于 `app/schemas/`。本节列关键字段与规则，精确类型、默认值和全部响应字段以对应源码为准。

| 文件 | 主要对象 | 字段与规则 |
| --- | --- | --- |
| `common.py` | `ApiResponse[T]`、`PageData[T]`、`ORMModel` | 统一 code/message/data/request_id；分页 items/total/page/page_size；from_attributes 支持 ORM 转换 |
| `auth.py` | `RegistrationRequest`、`SessionCreateRequest` | 注册用 department_id/name/invitation_code；登录用 department_id/name/shared_password；姓名 1～50 字符并规范化；密码与邀请码使用 SecretStr |
| 同上 | `DepartmentOption`、`CurrentUserRead`、`AuthSessionRead` | 部门选项、含部门名和角色的用户信息、user + csrf_token；会话原文由 Cookie 承载 |
| `organization.py` | `DepartmentCreate/Update/Read` | 创建/修改只接收部门名；Read 的 user_count/project_count/invitation_count 都是真实统计 |
| 同上 | `InvitationCreate/Read`、`UserRead` | 邀请码输入部门与可选预定姓名；输出可展示邀请码及实际使用人；UserRead 是系统注册成员 |
| `project.py` | `ProjectCreate/Update/Read` | 名称 ≤100、简介 ≤2000、上下文 ≤10000；创建可传 member_ids，不传 created_by；更新带 expected_revision；响应含两类修订号与统计 |
| 同上 | `ProjectMemberRead/List`、`ProjectMembersUpdate` | 返回成员顺序、任务数与 member_revision；更新提交非空、无重复的完整有序 user_ids 和 expected_member_revision |
| `task.py` | `TaskCreate/Update/Read` | 名称 ≤200、描述 ≤500；负责人必填；默认 NOT_STARTED/P1；版本与日期可空；更新必须带 expected_revision 和实际修改字段 |
| 同上 | `TaskList`、`TaskLaneRevision`、`TaskLaneOrderRead/Update` | 列表为 items/total/lanes，不是 PageData；排序提交完整 ordered_task_ids 和 expected_lane_revision |
| `version.py` | `VersionCreate/Update` | 名称 ≤100；创建必填起止日期和至少一名参与人；更新带 expected_revision，显式修改的字段不允许 null |
| 同上 | `VersionSummaryRead`、`VersionRead`、`VersionParticipantRead`、`VersionList` | 版本概要含总任务数与未完成数；详情额外含参与人及其在该版本的任务数；列表无分页 |
| 同上 | `VersionCompletionImpact`、`VersionDeleteResult` | 完成影响返回任务统计；删除返回解除关联数与 next_version_id |
| `requirement.py` | `RequirementCreate/Read` | 创建只接收 project_id/raw_content，内容去空白后不能为空且 ≤10000；响应带来源、10 个 AI 字段和分析状态 |
| 同上 | `BatchAnalyzeRequest/Accepted` | 1～50 个不重复的 32 位需求 ID；响应 RESERVED，尚不执行后台分析 |
| `interview.py` | `InterviewCreate`、`InterviewMessageCreate` | 文字或图片至少一项；文字 ≤10000；client_message_id 必填；每次最多 5 个不重复附件 ID |
| 同上 | `InterviewActionRequest`、`InterviewSummaryUpdate`、`InterviewConfirmRequest` | 动作含客户端消息标识；总结 fields 只允许定义的 11 类字段，字段值 ≤2000；确认带 idempotency_key |
| 同上 | `InterviewMessageRead`、`InterviewAttachmentRead`、`InterviewSessionRead`、`InterviewDraftRead`、`InterviewConfirmResult` | 消息/附件、卡片/问题、草稿摘要、会话+需求组合；不返回附件磁盘路径 |
| `dify.py` | `DifyAnalysisResult`、`DifyInterviewField/Fields/Question/Result` | AI 结果严格类型校验、禁止额外字段；重复需求必须给 related_id，非重复必须为空；validation_ok=false 拒绝访谈输出 |

`TaskUpdate` 中“不传某字段”和“传 null”不同：前者保留原值，后者只适用于可清空的版本与日期。仅更新一个日期时，要在 Service 合并数据库现值后重新检查日期关系。

访谈的 11 类字段是 `target_user`、`usage_scenario`、`user_goal`、`current_problem`、`expected_result`、`proposed_solution`、`frequency`、`impact_scope`、`bug_steps`、`actual_result`、`environment`。每个抽取字段携带 value、evidence_message_ids 和 source，source 用于区分用户输入和用户编辑。

## 六、Core 与请求依赖：身份和权限在哪里判断

### `app/core/config.py`

`BACKEND_ROOT` 固定定位后端目录，`.env`、相对 SQLite 文件和上传目录都按该目录解析，不依赖启动终端当前目录。`get_settings()` 在进程内缓存配置。

| 配置组 | 关键字段与默认行为 |
| --- | --- |
| 应用与数据库 | app_name、app_env、debug、api_v1_prefix；database_url 默认指向 data/requirements.db |
| 登录与安全 | shared_password、auth_hmac_key、invitation_encryption_key；session_cookie_name 默认 team_session，session_cookie_secure 默认 false |
| 会话期限与 CSRF | session_idle_days 默认 7；session_absolute_days 默认 30；csrf_enabled 默认 true；csrf_header_name 默认 X-CSRF-Token |
| 通用分析 | dify_base_url、dify_api_key、dify_workflow_path、dify_timeout_seconds、dify_candidate_limit |
| 访谈分析 | dify_interview_api_key、独立路径/超时、prompt_version、image_input_name |
| 附件 | interview_image_storage_dir；单张默认 10 MB，关联数量默认 5 |

### `app/core/security.py`

- `normalize_name()` 做 NFKC、去首尾空白和 casefold，用于同部门同名判断；`clean_display_name()` 保留展示大小写。
- 生成 9 位邀请码和随机会话令牌。
- 对邀请码、会话、CSRF 使用不同 purpose 的 HMAC-SHA256。
- 邀请码密文使用 Fernet；摘要密钥与加密密钥配置分开，相关操作要求密钥至少 32 字符。
- `shared_password_matches()` 使用恒定时间比较，统一密码为空时拒绝登录。

### `app/api/deps.py`

| 依赖 | 作用 |
| --- | --- |
| `DbSession` | 注入数据库 Session |
| `get_auth_context()` | 通过 Cookie 查找有效会话，把用户与会话上下文写入 request.state |
| `CurrentUser` / `get_current_user()` | 获取当前身份；自身不检查写请求 CSRF |
| `AuthenticatedUser` / `require_authenticated_request()` | 认证，并对 POST/PUT/PATCH/DELETE 校验 CSRF（配置启用时） |
| `AdminUser` / `require_admin()` | 在上述检查上要求 ADMIN 角色 |

项目、任务、版本、需求和访谈路由统一挂载登录与 CSRF 依赖；部门和邀请码路由内部要求管理员；系统成员列表对登录用户开放。注册、登录和登录部门选项不要求已有会话。

项目权限的进一步检查在 `ProjectService`：

- `get_visible()`：管理员可查看全部项目，普通成员仅能查看自己加入的项目；不可见项目返回 404。
- `require_member()`：业务修改要求操作者属于项目，未加入的管理员也不能直接修改项目业务。
- `require_writable()`：在成员身份基础上要求项目 ACTIVE。
- `save_members()` 是特例：活跃项目的现有成员以及管理员可维护成员集合，管理员可以先把自己加入项目。
- 归档项目只读；项目成员通过单独把 status 改为 ACTIVE 重新打开，不能在同次请求顺带修改其他资料。

### `app/core/exceptions.py` 与 `app/main.py`

`AppError` 携带 message/code/status_code/details；常见派生类为 `NotFoundError`（404）、`ConflictError`（409）、`AuthenticationError`（401）、`PermissionDeniedError`（403）、`InvalidImageError` 和 Dify 相关异常（502）。

`main.py` 将业务错误、请求参数错误（422）和 HTTPException 转成统一 JSON，并沿用或生成 `X-Request-ID`。成功响应为 code/message/data/request_id；标准错误另带 details。图片预览返回文件，不包在 ApiResponse 中。当前 CORS 明确允许 localhost:3000 和 127.0.0.1:3000 携带凭据访问。

## 七、Service 层：按业务 Review

### 7.1 `app/services/auth_service.py`

`register()` 校验邀请码摘要、状态、部门及可选指定姓名，创建 MEMBER 用户，条件更新邀请码为 USED，并在同一事务签发会话。`login()` 使用部门、规范化姓名与统一密码验证身份。

`resolve_session()` 拒绝过期或已撤销的会话，更新 last_seen_time，并将空闲期限续到“当前时间+配置天数”和绝对期限中的较早值。`revoke()` 撤销当前会话。`IssuedSession`、`AuthContext` 是内部 dataclass，不是数据库表或 API Schema。

Cookie 由 `api/routes/auth.py` 设置，使用 HttpOnly、SameSite=lax，当前 path 固定为 `/api/v1`；登录与注册成功都返回 user/csrf_token 并设置 Cookie。修改 API 前缀时，不能只改 Settings 而忽略这里的固定路径。

### 7.2 `app/services/organization_service.py`

一个文件包含三个 Service：

- `DepartmentService`：创建、改名、查询和删除部门；统计真实用户/项目/邀请码数量，有任一引用就拒绝删除。
- `InvitationService`：生成、加密保存、查询、解密展示和停用邀请码；已使用的不能停用；关键词支持预定姓名模糊匹配和完整 9 位邀请码匹配。
- `UserService`：按姓名关键词、部门筛选并分页返回注册用户；目前没有删除用户、修改用户角色或个人密码的管理 API。

### 7.3 `app/services/project_service.py`

`create()` 校验首批成员都已注册，创建人自动放在成员首位，并为成员建立 TaskLane。`list()/get()` 返回可见项目及真实需求数/成员数；`update()` 修改资料、归档或重开，使用 revision 防止旧页面覆盖新数据。

`save_members()` 接收完整有序列表，并使用 member_revision 条件更新：

1. 仍负责任意任务（包含已完成/取消）的成员不能移除，需先转交或删除任务。
2. 移除会让某个版本失去最后一位参与人时拒绝操作。
3. 可移除时清理对应版本参与关系和泳道，并提升受影响版本的 revision。
4. 新成员创建成员关系和泳道；按提交顺序写入 sort_order。

成员集合至少保留一人；排序由这一处维护，版本参与人显示与任务列表成员顺序都引用它。

### 7.4 `app/services/task_service.py`

`list()` 按项目、任务名称关键词、状态和可选版本筛选；先按项目成员顺序，再按负责人内部任务顺序返回。返回完整结果和泳道修订号，**没有“只取前 200 条”的截断逻辑**。

`TASKS_PER_ASSIGNEE_LIMIT = 200` 限制的是“同一项目中，同一负责人当前持有的任务总数”，不按创建人统计，也不按单个版本统计。创建和转交都会检查；已完成/已取消任务计入上限，永久删除后才释放对应数量。

`create()/update()` 校验项目可写、负责人属于项目、版本属于同项目、日期合法；关联版本时自动补齐负责人到版本参与人中。转交任务移动到新负责人队尾，并更新新旧泳道修订号。

`delete()` 按 expected_revision 永久删除任务并更新泳道修订号。`get_lane_order()/reorder_lane()` 读取或保存该负责人在项目内的完整任务顺序；筛选后的局部列表不能直接当作完整顺序提交。

### 7.5 `app/services/version_service.py`

- `create()`：参与人必须来自当前项目，创建时至少一人，版本名在项目内唯一。
- `list()/get()`：按创建时间倒序展示版本，统计总任务数和未完成数；参与人按项目成员顺序返回，允许没有任务。
- `update()`：检查版本 revision、合并后的日期和参与人变化；仍负责当前版本任务的人不能移除。
- `completion_impact()`：返回总数和未完成数，为前端确认提供信息。
- `delete()`：删除版本和参与关系，在同一事务清空相关任务 version_id、增加任务 revision，并返回解除关联数及最新剩余版本 ID。

完成或重新打开版本只改变版本状态，**不会自动批量修改任务状态**；完成版本本身不等于项目归档，也不会因此禁止任务编辑。

### 7.6 `app/services/requirement_service.py`

`create_and_analyze()` 处理直接提交；`create_from_interview()` 处理访谈确认结果。都先提交 PENDING 需求，再执行 `analyze_existing()`：

1. 写入 ANALYZING，清空上次错误。
2. 读取同项目最近已分析的候选需求。
3. 优先用 clarified_content，否则用 raw_content 调用 Dify。
4. 成功写入固定 10 字段与 Workflow ID，状态为 ANALYZED。
5. 捕获可控 AI 错误时保留需求，记录错误并标为 FAILED。

`list()/get_visible()` 限制用户可见范围。直接创建的项目可写检查由路由先调用 ProjectService；Service 中的 `get()` 是内部查询，不等同于 `get_visible()`。

### 7.7 `app/services/interview_service.py`

负责创建会话、保存消息、图片绑定、抽取字段合并、跳过/不清楚、人工总结编辑、确认生成需求、放弃与草稿查询。`to_read()` 将 JSON 文本和 ORM 关系组装成卡片、当前问题和消息列表。

典型状态为 DRAFT → INTERVIEWING → CONFIRMING → SUBMITTED；也可从首轮直接进入 CONFIRMING，未提交会话可放弃。FAILED 是保留枚举，当前流程不会主动将会话设为 FAILED。

停止追问的依据包括连续两次 Agent 失败、连续两次跳过、轮数达到上限（BUG 5 轮，其余 4 轮）、完整度达到 80 且满足类型要求，也支持直接整理。用户编辑字段在后续合并中优先保留。

Review 幂等时分开看：创建使用 source_channel + source_message_id，消息使用 session_id + client_message_id；确认保存 confirm_idempotency_key，已有关联 requirement_id 时直接返回原需求。确认生成需求分多次 commit，不应描述成覆盖 AI 调用的单一数据库事务。

### 7.8 `app/services/interview_attachment_service.py`

`upload()` 检查扩展名、Content-Type、PNG/JPEG/WEBP 魔数及大小，使用随机 ID 作为存储文件名；先写磁盘，再写记录，数据库提交失败时删除本次文件。`bind_to_message()` 检查附件存在、上传人及会话/消息绑定，随后 flush，由上层流程提交。

`content_path()` 检查真实路径在上传目录内且文件存在。访问权限在访谈路由处理：已绑定附件按项目可见性检查，未绑定附件只允许上传者预览。上传本身在绑定项目前进行。

### 7.9 两个 Dify 客户端

| 文件 | 入口与作用 | Review 关注点 |
| --- | --- | --- |
| `app/services/dify_service.py` | `analyze_requirement()` 发送项目上下文、需求和候选列表 | 使用 DifyAnalysisResult 校验提取结果；related_id 必须来自当前项目候选；兼容顶层字段和 outputs.result |
| `app/services/dify_interview_service.py` | `run_turn()` 发送历史、字段、动作及图片；必要时先上传图片 | 按 interview:session_id 隔离图片身份，缓存上传 ID；使用 DifyInterviewResult 校验访谈输出 |

两者使用 blocking 模式的异步 HTTP 调用，并设置 `trust_env=False`；区分配置、网络、超时、执行和输出格式错误。返回的 `DifyWorkflowResult`、`DifyInterviewWorkflowResult` 是内部 dataclass。本节描述本地封装，不能据此认定实际 Dify 服务或线上 Workflow 已被验证。

## 八、并发与排序字段速查

| 字段 | 管理范围 | 客户端提交 | 典型冲突码 |
| --- | --- | --- | --- |
| `Project.revision` | 项目资料与状态 | expected_revision | PROJECT_REVISION_CONFLICT |
| `Project.member_revision` | 成员增删及成员顺序 | expected_member_revision | PROJECT_MEMBER_REVISION_CONFLICT |
| `Task.revision` | 单条任务修改、删除及解除版本关联 | expected_revision | TASK_REVISION_CONFLICT |
| `TaskLane.revision` | 项目某负责人任务集合与排序 | expected_lane_revision | LANE_REVISION_CONFLICT |
| `ProjectVersion.revision` | 版本资料、状态与参与人变化 | expected_revision | VERSION_REVISION_CONFLICT |

修订号从 1 开始，客户端带上读取时的版本号，Service 用带条件的 UPDATE/DELETE 判断是否过期。项目成员 `sort_order` 排人；任务 `sort_order` 排同一负责人的任务；版本参与人没有独立排序。

任务纯排序修改 sort_order 和泳道修订号，不增加每条任务 revision。删除版本增加相关任务 revision；自动补齐参与人会增加版本 revision。Review 时应看具体操作更新的是哪种修订号，不能把所有 revision 视为同一个全局版本号。

| `requirements.py`（5） | /requirements；/{requirement_id}；/{requirement_id}/interview；/batch-analyze（后面均接在 /requirements 下） | 创建/列表/详情、关联访谈、批量分析预留 |
| `interviews.py`（12） | /interviews 下的 drafts、attachments、{session_id}、messages、actions/skip、actions/unknown、actions/summarize、summary、confirm、abandon | 访谈与附件完整流程；attachments/{attachment_id}/content 返回图片文件 |

任务和版本的删除接口通过 **Query 参数 expected_revision** 接收修订号，不是请求体。项目归档/重开、版本完成/重开都使用各自 PATCH 接口修改 status，没有独立的 archive/complete API。

## 十、沿着业务流程找代码

### 注册并进入项目

1. `organization.py` → `InvitationService.create()` → 邀请码摘要和密文。
2. `auth.py` → `RegistrationRequest` → `AuthService.register()` → 用户、邀请码核销和会话。
3. 再次访问经 `api/deps.py` 解析会话，身份进入 request.state。
4. `projects.py` → `ProjectCreate` → `ProjectService.create()` → 项目、首批成员和空泳道。

### 创建关联版本的任务

1. `tasks.py` 接收 project_id 和 `TaskCreate`。
2. `TaskService.create()` 校验项目可写、负责人和版本归属、日期。
3. 更新泳道、检查当前负责人 200 条上限、分配队尾 sort_order。
4. 保存 Task；必要时增加 VersionParticipant 并提升版本 revision。
5. 提交事务并返回 TaskRead。版本排期再按 version_id 查询同一批任务。

### 访谈确认生成需求

1. 可选图片先经 `InterviewAttachmentService.upload()` 保存。
2. `interviews.py` 检查项目可写，再由 `InterviewService` 保存会话/消息和绑定图片。
3. `DifyInterviewService` 生成抽取字段/下一问，`InterviewService` 合并并决定状态。
4. 用户确认后由 `RequirementService.create_from_interview()` 保存正式需求，再调用通用分析客户端。
5. 无论可控 AI 分析成功或失败，已保存需求都保留；会话记录关联需求并标为 SUBMITTED。

直接提交需求则从 `requirements.py` → 项目可写检查 → `RequirementService.create_and_analyze()` 开始。AI 失败时接口仍返回已保存需求，业务 code 为 AI_ANALYSIS_FAILED，不能只看 HTTP 状态判断分析是否成功。

## 十二、推荐 Review 顺序与代码边界

建议先从新增最多的身份、项目成员、任务和版本开始：

1. `app/main.py` → `app/api/router.py` → `app/api/deps.py`，弄清入口和身份。
2. `app/db/models.py`，重点看 UserAccount、ProjectMember、TaskLane、Task、ProjectVersion、VersionParticipant。
3. `schemas/auth.py` / `services/auth_service.py`，看注册与会话。
4. `schemas/project.py` / `services/project_service.py`，看权限、成员和排序。
5. `schemas/task.py` / `services/task_service.py`，看任务上限、转交和并发。
6. `schemas/version.py` / `services/version_service.py`，看参与人、共用任务和删除行为。
7. 再看需求、访谈、附件与两个 Dify 客户端。
8. 对照各模块路由和测试，最后核对迁移能否建立模型所需结构。

每看一个写操作，确认：操作者从哪里来；权限在哪检查；请求字段和数据库字段如何转换；哪个修订号参与检查；何时 flush/commit/rollback；失败或重试会不会留下部分结果。

当前已实现登录注册、邀请码核销、真实系统成员、项目编辑/归档/重开、成员排序、任务与版本、Alembic 和健康/就绪检查。尚无真实后台批量分析队列、用户删除/个人密码管理、独立需求转任务关联、附件对象存储和完整操作审计。多个来源渠道虽有枚举，当前创建访谈仍走管理端入口。

本篇是代码导航，不是新的产品方案，也不代表已完成生产部署或真实 AI 服务联调验收。
